## 1. 目的

同時に最大4セッションを表示するキーボードで、あるセッションが承認待ち／入力待ちになったとき、
**作業中の画面を一度も奪わずに**、手元の操作だけで回答を完了できるようにする。

---

## 2. 設計の起点：ScreenKey は「読む面」になれない

ScreenKey は 0.85インチ対角・128×128 である。一辺 15.3mm、画素ピッチ 0.119mm。

可読性の目安（視角20分）で必要な文字高は `視距離 × 0.0058`。

| 視距離 | 必要な文字高 | ピクセル | 入る行数 |
|---|---|---|---|
| 50cm（前傾） | 2.9mm | 24px | 5行 |
| **60cm（通常の着座）** | **3.5mm** | **29px** | **4行** |

実際に載る量は **和文16字**または **ASCII 30字**程度である。キートップは斜めから見るため、
実効的にはさらに減る。

```text
$ git push origin feat/ai-response-transfer-keys   ← 45字。入らない
```

diff は何インチあっても載らない。**したがって「ScreenKey に選択肢や要求内容を出し、それを読んで
番号で答える」という置き換え対象2文書の共通前提は成立しない。**

置き換え対象文書はこの制約を「文字列を wire へ載せない」という設計方針として持っていたが、
それは状態表示機能から引き継いだ制約であって、物理的制約とは別物である。**物理的制約のほうが
厳しく、そちらが設計を決める。**

---

## 3. 設計原則：役割を3つに分ける

| 軸 | 担当 | 理由 |
|---|---|---|
| **気づく／どれか** | ScreenKey ×4 | 色・アイコンなら視距離が効かない。4画面あるので並行して待機中のセッションが一目で分かる |
| **読む** | **HUD**（モニタ上の小さな常時最前面パネル） | 解像度が要る。既に見ている面である |
| **決める** | 物理キー・エンコーダ | **現在のフォーカスを一切動かさずに確定できる唯一の入力装置** |

### 3.1 なぜ HUD がターミナル前面化より優れるか

承認1回のコストは打鍵時間ではない。**対象の画面へ移動すること**と**元の作業へ戻ること**である。
置き換え対象2文書はどちらも必ずターミナルを前面化するため、このコストを毎回払わせる。

HUD は非アクティブ・最前面ウィンドウとして表示するため、

- **フォーカスを取らない。** エディタのキャレットは残り、打鍵も止まらない
- **ウィンドウ配置を壊さない。** だから「元に戻る操作」が発生しない
- 常に同じ場所に出る。探す必要がない
- Codex にも Claude Code にも同じ UI を出せる

これは KO-1 で実測済みである（§4）。

### 3.2 なぜ決定を物理キーで行うか

HUD が出ているならマウスでクリックすればよい、とはならない。**クリックはフォーカス移動を伴う**ため、
その瞬間に「戻る操作」が復活する。物理キーは、現在のフォーカスを1ミリも動かさずに決裁できる
唯一の手段である。

### 3.3 選択肢の序数一致問題が消える

置き換え対象2文書が共通で抱えていた「Host が思う選択肢の順番と、ターミナル画面の順番が一致するか」
という問題は、**選択肢を HUD に出した瞬間に消滅する**。ユーザーが読むリストと Host が返すリストが
同一のデータになるためである。ターミナルの表示順は無関係になる。

## 4. 実測で確定した前提（3つのゲート）

| # | 問い | 結果 |
|---|---|---|
| KO-1 | HUD は表示・反復・更新でフォーカスを奪わないか | ✅ 2つの独立した計測器でイベント0件。最大化ウィンドウより前面、Alt+Tab・タスクバーに出ない、DPI 150%/200%、マルチモニタで確認 |
| KO-3 | Claude Code へ回答を注入できるか | ✅ `PermissionRequest` hook の decision で承認・拒否が通る。拒否理由がモデルに届く |
| KO-2 | Codex へ代理応答できるか | ✅ **保持・同時転送（`race`）とも成立**。`race`ではHUD/CLIの先着回答だけで要求が解決し、遅着回答で再実行もJSON-RPCエラーも起きない |

### 4.1 どちらのクライアントもフォールバックが自動的に存在する

- **Claude Code**: hook の応答を待たずに約3秒でターミナルにもプロンプトが出る。
  Studio が落ちていれば、いつもどおりターミナルで答えられる。固まらない
- **Codex**: 要求を最初から CLI へ転送する。HUDとTUIのどちらでも直ちに回答でき、片方が
  使えなくてももう片方を待つ必要がない

**HUD は「あれば速い」便利層であり、無くても何も壊れない。** 当初の懸念（Studio 停止時に
AI クライアントが固まる）は実測で否定された。

## 5. 体験の全体像

```text
[平常] 4画面がセッション状態を表示。作業に集中している
   │
   │ Codex が承認待ちになる
   ▼
[気づく] 対象の ScreenKey が黄色く点滅する
   │      同時にモニタ隅へ HUD が現れる（フォーカスは動かない）
   │
   │ 視線を HUD へ。全文と選択肢を読む
   ▼
[決める] ✅ を押す ／ エンコーダを回して選び ✅ を押す
   │      拒否したいときは ❌ でハイライトを拒否側へ寄せてから ✅
   ▼
[復帰] 押した ScreenKey が 0.7 秒だけ確定表示を出し、HUD が消える
       作業画面は最初から一度も動いていない
```

複数が同時に待機しているときは、答えたいセッションの **ScreenKey を押す**と HUD の内容が
それに切り替わる。どれが選ばれているかは ScreenKey の白い L 字と明るさで分かる（§8）。

## 6. ハードウェア割当

> 2026-09-06、実HID（aipad）で全面的に見直した。**長押しは一切使わない。**
> 決定の経緯は §6.5。以下の表は実装済みの内容である。

### 6.1 ScreenKey ×4

意味は **「このセッションを相手にする」** で一貫させる。**実装済み。**

| 状況 | 短押し |
|---|---|
| 待機中（`WAITING_APPROVAL` / `WAITING_INPUT`） | **HUD の対象をこのセッションにする** |
| それ以外 | 対応ターミナルを前面化（**現行 `FocusAiTerminal` の挙動**） |

Host は `HOST_ACTION` の `action_id` と `value` しか受け取らないため、**この分岐は Host 側で行う**。
`SelectHudTarget` がそのスロットに承認待ちを見つけられなければ、`FocusAiTerminal` と同じ処理へ
フォールバックする（`actions.rs`）。Firmware は 1 種類の `action_id` を送るだけでよい。

**回答の意味には使わない。** 位置で意味が変わるとモード錯誤が起き、
「許可のつもりで拒否」という最悪の誤操作を生む。また4画面が状態表示を失うことは、
最も忙しい瞬間にこの製品の中心価値を手放すことになる。

### 6.2 通常キー

| キー | 単押し |
|---|---|
| **✅ 承認**（緑キーキャップ） | **現在ハイライトされている選択肢を送信する。** 唯一の送信経路 |
| **❌ 拒否**（赤キーキャップ） | **拒否側の選択肢へハイライトを移動する。何も送信しない** |
| **TRANSFER** | `ai-response-transfer-design.md` の転送モード（未実装） |
| 予備 | ユーザー自由 |

**❌ は「拒否を送るキー」ではなく「拒否側を選ぶキー」である。** 移動先は
`available_decisions` の中の完全一致 `"decline"`、無ければ完全一致 `"cancel"`、
どちらも無ければ移動しない。

**なぜこうしたか。** `codex-cli 0.153.2` の実測では、コマンド承認・ファイル編集承認とも
`available_decisions` は `accept` / `acceptWithExecpolicyAmendment` / `cancel` の 3 種だけで、
**`decline` は一度も提示されなかった**。「❌ ＝ `decline` を送る」という当初の設計は、
実機で必ず no-op になる。かといって `decline` の代わりに `cancel` を自動送信すると、
turn 中断と拒否を意図的に区別してきた境界（§16）を崩す。

ハイライトを動かすだけなら、**送信するのは ✅ を押したユーザーの明示的な意思**であり、
この境界を保ったまま ❌ が機能する。取り返しのつかない操作に 2 打鍵を要求する点でも、
400 ms guard と同じ思想に沿う。

`Fn` と `☑ トグル` は置かない。複数選択を伴う要求は現時点で存在せず、
「常に許可」（§9.3）も未実装のため。

### 6.3 エンコーダ

一貫した意味は **「中身を進める」**。

| 状況 | 回す | 押す |
|---|---|---|
| 選択肢が出ている | HUD のハイライトを進める | — |
| 平常時 | 普段の用途（ハードウェア次第） | — |

**押しボタンは使わない。** aipad に実装されている EC12E1220301 には押しスイッチが無い。

回転は ZMK 標準の `zmk,behavior-sensor-rotate`（`_var` の付かない方）で `host_action` を
ラップする。`_var` 版は方向ごとに 1 パラメータしか渡せず、`host_action` の 2 パラメータを
固定できない。**Firmware 側の新規 behavior 実装は不要。**

```dts
hud_rotate: hud_rotate {
    compatible = "zmk,behavior-sensor-rotate";
    #sensor-binding-cells = <0>;
    bindings = <&host_action 4 0>, <&host_action 5 0>;
};
```

`bindings` の [0] が CW、[1] が CCW である。**ただし実機の体感方向はエンコーダの A/B 相の
配線に依存する。** aipad では配線の向きが ZMK の CW 定義と逆で、意図した操作感にするため
入れ替えている。仕様と逆に見えるが正しい。

**回すだけでは何も確定しない。** 可逆な操作にだけ回転を割り当てる。

### 6.4 レイヤ切替

**使わない。すべて layer 0 に置く。**

当初は capability bit 0 `APP_LAYER` で「HUD 表示中だけ AI 回答レイヤへ切り替える」ことを
想定していた。狙いは、非表示時にエンコーダと通常キーを普段の用途へ戻すことだった。

aipad を **AI 操作専用のマクロパッド**とする判断により、この必要が無くなった。
切り替えなければ Host 側の layer set/clear の実装も不要になる。
引き換えに、エンコーダの平常時の用途（音量など）は失われる。

### 6.5 長押しを使わない理由

`HOST_ACTION` は `action_id` と `value` の 2 バイトだけで、**Host からは短押しと長押しを
区別できない**。長押しを使うなら Firmware 側に hold-tap を組んで別の `action_id` を
送らせることになる。

そこまでして得るものが無い。承認は「速く、安全に」が価値であり、**長押しは速さを削る割に
誤爆防止としては 400 ms guard に劣る**。また §6.1〜§6.3 の割当は ScreenKey 4 個・通常キー
2 個・エンコーダ回転で足り、キー数の節約という動機も無い。

したがって **本設計に長押しは存在しない。** §12 の「中断は ❌ 長押しのみ」も、
❌ → ✅ の 2 打鍵（`cancel` の明示的な選択）へ置き換わった。

## 7. HUD の仕様

### 7.1 ウィンドウ

Tauri の別 `WebviewWindow` として実装する。`crates/rawhid-host-tauri/src/hud_window.rs`
（KO-1 で作成済み）をそのまま使う。

- `visible(false)` / `focused(false)` / `always_on_top(true)` / `skip_taskbar(true)` /
  `decorations(false)` / `resizable(false)` で生成
- 生成直後・初回表示前に ExStyle へ `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`
- 表示は `SetWindowPos(HWND_TOPMOST, ..., SWP_NOACTIVATE | SWP_SHOWWINDOW)`、
  非表示は `ShowWindow(SW_HIDE)`。**Tauri の `show()` / `hide()` は使わない**
- WebView2 の生成は起動時に1回だけ

**HUD は入力を一切受けない。** 承認キーもエンコーダも HID 経由で Studio プロセスへ直接届くため、
HUD にフォーカスを渡す理由が構造的に存在しない。

### 7.2 表示内容

```text
┌──────────────────────────────────────────┐
│ Codex · keylink-studio                   │  どのセッション
├──────────────────────────────────────────┤
│ コマンド実行の許可                          │  要求の種別
│                                          │
│  mkdir ko2-test                          │  ★主表示
│                                          │
│  作業ディレクトリ: C:\01.keyboards\...      │
│  理由: ワークスペース内に ko2-test ディレク  │  AIが書いた理由
│        トリを作成してよいですか？            │
├──────────────────────────────────────────┤
│  ▸ 許可                                  │  ★選択肢
│    mkdir を今後許可                        │  エンコーダで ▸ が動く
│    中止                                  │
├──────────────────────────────────────────┤
│  ⟳ 選ぶ    ✅ 決定    ❌ 拒否側へ           │
└──────────────────────────────────────────┘
```

| 表示項目 | Codex | Claude Code |
|---|---|---|
| **主表示** | `commandActions[].command` | `tool_input.command` |
| コマンド全文 | `command`（`powershell.exe -Command '...'` を含む冗長な形。副次表示） | — |
| 理由 | `reason`（**AI がユーザーの言語で書く**。実測は日本語） | — |
| 作業ディレクトリ | `cwd` | `cwd` |
| ツール種別 | `kind` | `tool_name` |
| 選択肢 | `availableDecisions`（**要求ごとに読む**） | Host 側で `allow` / `allow_with_permissions` / `deny` を正規化（§9.2・§9.3） |

**Codex の `command` をそのまま主表示にしてはならない。** `powershell.exe -Command '...'` の
ラッパに本質が埋もれる。

### 7.3 実装上の注意

- **HUD のサイズは DPI を考慮した論理単位で指定すること。** KO-1 のプローブは物理ピクセル
  指定（420×260）だったため、高DPI環境では表示面積が実質的に縮む
- **本番の HUD ページは Vite にバンドルされる通常のルートとして作ること。**
  素の HTML を `ui/public/` に置くと `@tauri-apps/api` を import できず、
  `withGlobalTauri`（本番 `main` ウィンドウにも `window.__TAURI__` を露出させる設定）が必要になる
- クリックすると 20ms 未満だけ HUD が前面化する（KO-1 の C7）。表示専用なので実害はないが、
  排除するなら `WM_MOUSEACTIVATE` で `MA_NOACTIVATE` を返す

## 8. ScreenKey の表示

`AI_CLIENT_STATE` を **8→9バイト**へ1バイト拡張する。capability **bit 14**
（`AI_CLIENT_SCREENKEY_STATE`）を新設する（bit 13 まで使用済み）。
**2026-09-06、Host・Firmware とも実装し、実HID で受け入れ済み。**

**9バイト目は表示状態だけを載せる。** 既存 8バイトのバイト割りと意味は変更しない。

| 値 | 意味 | 描画 |
|---|---|---|
| 0 | 通常 | 従来どおり |
| 1 | 待機中・**HUD の対象** | 明るい黄枠＋白い L 字＋淡い黄背景（下記） |
| 2 | 待機中・対象ではない | 暗い黄枠＋ロゴを減光（下記） |
| 3 | 回答を送信した直後 | 緑の円と白いチェックの 0.7 秒アニメーション（下記） |

- 未広告のデバイスへは従来の 8バイトを送る
- **9バイトを送るのは bit 14・bit 13・bit 11 の 3 つすべてを広告する機体に限る。**
  9バイト payload は 8バイト payload の上位互換だからである
- **同報でよい。unicast はしない**（理由は後述）

### なぜこの表示が要るか

承認待ちが 2 セッション同時に起きると、4 枚の ScreenKey が同じ黄色点滅になり、
**どれが HUD に出ているのか＝ ✅ がどれに効くのかが画面から分からない。**
ScreenKey は「対象を選ぶキー」なのに、選んだ結果が返ってこない状態だった。

### 対象と非対象（値 1 / 値 2）

| | 値 1 対象 | 値 2 非対象 |
|---|---|---|
| 黄枠 | `0xFACC15` | 暗い黄 `0x645208`（約 40%） |
| 点滅 | する | **する。対象と同じ周期・同じ位相** |
| ロゴ | そのまま | **黒を 60% 混色して減光** |
| ロゴを囲む白い L 字 | **あり（静止）** | なし |
| 背景の淡い黄塗り | あり（15%） | なし |

ロゴは Codex / Claude Code とも 88×88 の RGB565 で、L 字はその外側 6px を囲む位置に置く。
線幅 2px、白 `0xFFFFFF`。減光は `img_recolor` に黒を混ぜて行う。recolor は各画素と指定色の
線形ブレンドなので、**色相を保ったまま明るさだけが落ちる**。`img_opa` は背景へ溶かす動作に
なり結果が背景色に左右されるため使わない。

### なぜ「静止＝対象」をやめたか

**2026-09-06、当初の設計を破棄した。** 当初は「対象＝点滅を止める」とし、
「**動いている＝未処理、静止している＝いま相手にしている**」という対比を作るとしていた。
周辺視野では動きの有無が最も強く効く、という前提自体は正しい。**向きが逆だった。**

実機で、**点滅している方が HUD に出ていると読まれた。** 動きは「注意を引く」信号であり、
人は動いているものを「いま生きている・自分に関係のあるもの」と読む。「静止＝選択中」は、
規則を覚えていないと読めない恣意的な対応でしかなかった。

さらに悪かったのは、**同じ語彙（黄色の枠）の有無だけで区別していた**ことである。
「点滅する黄枠」と「点滅しない黄枠」は量の違いでしかない。**区別すべきものは、
種類が違って見える必要がある。**

そこで、2 つの問いを別々のチャンネルへ分けた。

- **「返事待ちかどうか」＝ 黄色と点滅。** 4 枚とも同じように点滅するので、
  点滅は対象の情報を一切持たない。誤読が構造的に起きない。気づかせる力は落ちない
- **「どれが HUD に出ているか」＝ 白い L 字と、全体の明るさ。**
  L 字が主、明るさが従の冗長な符号化である

**4 枚の点滅は 1 つの共有タイマーから駆動し、同位相にしなければならない。**
対象と非対象の区別は明るさの差であり、点滅も明るさを変える。位相がずれていると
「明るい枠の消灯中」と「暗い枠の点灯中」が同時に見え、**明暗が逆に読める**。
白い L 字を静止させているのはその保険でもある。点滅のどの瞬間に目を向けても
L 字は必ずそこにあるので、対象がどれかは明るさに頼らず読める。

### 送信直後（値 3）＝ 緑の円と白いチェック

合計 0.7 秒。中央に緑 `0x22C55E` の塗りつぶし円（直径 52px）がスケールインし、その内側に
白いチェックのストロークが引かれ、保持してから通常へ戻る。
**アニメーション中はロゴを消し、完了後に再表示する。**

これが無いと、✅ を押しても HUD が消えるだけで、**キーボードを見ている目には何も起きない。**

当初は「外周に緑のリングを一周描く」としていたが、**2026-09-06 に破棄した。**
外周はキーキャップの縁で物理的に見切れる。図柄は中央 96×96px の内側へ収める。

**タイマーは Firmware が持つ。** Host は 0.7 秒後に送り直さない。
既存の `COMPLETED`（5 秒保持）と同じ流儀である。

### なぜ Host が値 3 を保持し続けるか

当初は「Host は値 3 を 1 回送るだけ」としていた。**2026-09-06 に破棄した。**

✅ を押すと承認が解決し、`WaitingApproval` → `Working` の状態変化が起きる。Host はこの変化を
最大 500ms 以内に送るため、**1 回だけでは 0.7 秒のアニメーションが描き切る前に上書きされて
消える。**

そこで Host は、✅ から **850ms のあいだ 9バイト目を値 3 で上書きし続ける**
（`HUD_RESPONDED_HOLD`）。Firmware の再生 700ms を確実に覆うための値である。両者は開始点が
ずれる。Host は `HOST_ACTION` を処理した瞬間に保持を始め、Firmware は後続の HID 書き込みが
届いてから再生を始めるため、再生時間と同じ保持では最終フレームが欠ける。

**上書きするのは 9バイト目だけで、0..8 バイト目は最新の状態を運び続ける。**
状態表示そのものが遅れることはない。

この方式は、Firmware 側の 2 つの取り決めを前提にしている。

- **再生中に再度 値 3 を受け取っても、描き直さず継続する。**
  無ければ 850ms のあいだ繰り返し描き直され、チェックに到達しない
- **再生中に 値 3 以外を受け取っても、下地を描き替えない。**
  保留し、再生完了後に最新の状態を適用する。無ければ下地の再描画でアニメーションが消える

### 種別アイコンは載せない

当初は `▶ 実行 / ✎ 編集 / ⬇ 取得 / ？ 質問 / ⚠ 要注意` の固定 enum を右下に出す案だった。
**2026-09-06、載せないことに決めた。**

- **アイコンは「HUD を読まずに判断する」を誘発する。** ✎ が出ていれば「編集か、では許可」と
  押せてしまうが、**どのファイルを編集するのかはアイコンからは分からない**。§2 の前提は
  「ScreenKey は読む面になれない」であり、400 ms guard も ❌ の 2 打鍵化も「押す前に読ませる」
  ための仕掛けである。判断材料になりきらない情報をキーの上に置くと、その安全策と逆に働く
- **効く場面が限られる。** アイコンが情報を足すのは「2 件以上が同時に承認待ちで、HUD に
  出ていない方の中身を知りたい」ときだけで、その場合も ScreenKey を押せば HUD で読める

これにより 9バイト目は表示状態 4 値だけで足り、Host 側のメソッド名→アイコンの対応付けも、
Firmware 側のシンボルフォント（Flash 増）も不要になった。**チェックも `lv_line` の
ストロークで描き、フォントを積まない**（現行 `status_screen.c` は矩形と画像だけで描いている）。

**文字列を wire へ載せる経路は作らない。** これは恒久的な境界である。

### なぜ unicast にしないか

設計当初は「押した個体へ unicast する（同報すると他のキーボードの表示が変わる）」としていた。
**2026-09-06、同報でよいと判断した。**

HUD の対象は**アプリ全体で 1 つ**である。複数のキーボードが同じ表示スロットを映しているなら、
**どれもが「これが対象だ」と示すのは事実に忠実**である。unicast にすると逆に、
同じセッションを映しているのに対象表示にならない画面ができ、そちらの説明が要る。

実装上も、既存の送信ループは capability を見て送る内容を出し分ける構造になっているため、
同報のままなら **bit 14 を持つ機体には 9バイト、持たない機体には従来どおり**という分岐を
1 本足すだけで済む。unicast は送信経路に宛先の概念を新しく持ち込むことになる。

## 9. 回答経路

### 9.1 Codex（同時転送＋first-wins方式）

**Broker は `item/commandExecution/requestApproval` を記録しつつCLIへ転送する。HUDとTUIを
同時に生かし、先に確定した回答だけをApp Serverへ送る。**

```text
App Server ──requestApproval──> [Broker: Pending] ──requestApproval──> CLI/TUI
                                     │                         │
                                     └──────> HUD               │
                                               │                │
                               先に回答した側 ─┴────────────────┘
                                               │
App Server <────────────response(decision)─────┘
```

2026-09-05のKO-2追加検証では、`race`モードでHUD相当の回答が先着するとTUIの承認画面が
自動的に閉じ、コマンド結果は1回だけ表示された。CLIの`accept`が先着したランでは、要求から
約1.94秒後にCLIが応答し、1ms後に`serverRequest/resolved`、約3.28秒後に
`turn/completed(status=completed)`を観測した。さらに約8秒後、検証用プローブが意図的に
重複`accept`を送ってもJSON-RPCエラーと再実行は起きなかった。CLI先行`cancel`でも、遅着した
プローブの`accept`で実行へ反転せず、turnは`interrupted`のままだった。

プローブは重複耐性を測るため遅着responseも意図的に送ったが、**製品実装はその耐性へ依存しない。**
要求ごとにfirst-winsの排他制御を置き、先着回答を転送した後のHUD操作／CLI responseは破棄する。
App Serverの`serverRequest/resolved`を観測した時点でもHUDを閉じ、要求を`Resolved`へ進める。

- `decision` は `availableDecisions` の要素を**そのまま不透明値として**返す。
  文字列とオブジェクトが混在するため、再構築してはならない
- `availableDecisions` の**集合は要求ごとに変わる**。実測では `accept` /
  `acceptWithExecpolicyAmendment` / `cancel` の3つで、`decline` も `acceptForSession` も
  含まれていなかった。Host が固定の選択肢集合を持ってはならない
- `availableDecisions` が無い／空なら HUD からの回答を有効にせず、そのまま CLI へ転送する

保持方式は技術的な縮退候補として残すが、通常経路には採用しない。要求をCLIへ見せないため、
HUDが使えない場合に遅延転送タイマーが必要となり、ユーザーが回答できるまで不要に待たされるためである。

2026-09-05 に `host_approval_lifecycle_e2e_uses_real_broker_and_selected_thread_only` を通した。
localhost の mock App Server は上流だけを代替し、製品の Broker WebSocket 転送、
`CodexActivityRuntime` / `PendingApprovalStore`、HUD の純粋選択状態、Host response dispatcher を
実際に接続した。同一 connection の2 threadから ScreenKey の表示対象 thread だけを選び、400 ms
guard 後の decision、Host先行／CLI先行のfirst-wins、`decline` と `cancel` の分離、切断時の pending
解放を自動確認した。実 Codex CLI プロセス、Tauri GUI、実HIDはこのテスト範囲外である。

段階2のHost側実装は次のコミットで構成する。

| commit | 内容 |
|---|---|
| `37532b8` | `Pending → Resolving → Resolved`のfirst-winsと、タイムアウト済み要求を後から実行しない応答経路 |
| `832471c` | HUDの対象・選択肢・400 ms guardを管理する操作状態 |
| `7965aee` | 表示対象threadへ物理`HOST_ACTION`を接続。**この時点では短押しRejectを`decline`送信としていた**（下記 `752fbff` で置き換え） |

### 9.2 Claude Code（hook decision）

**実装済み・実機受け入れ済み（2026-09-06）。** `claude_observer.rs` は `PermissionRequest` に
限り 204 の代わりに decision を返す。**他の hook はすべて 204 のまま維持**し、観測専用の隔離を
保っている。

```json
{"hookSpecificOutput":{"hookEventName":"PermissionRequest",
  "decision":{"behavior":"allow"}}}
```

```json
{"hookSpecificOutput":{"hookEventName":"PermissionRequest",
  "decision":{"behavior":"deny","message":"ユーザがこの操作を拒否しました。"}}}
```

- **hook 接続を開いたまま待つ。** `ClaudePermissionGate` が、待っている hook 接続と Host 側の
  回答を token（`claude_key` の不透明値）で突き合わせる。要求1件につき待ち口は1つで、
  **答えは1回しか通らない**
- **hook の `timeout` は `PermissionRequest` だけ 60 秒**（他は据え置きの1秒）。Host 側は 55 秒で
  自分から 204 へ降りる。Claude Code に打ち切られる前に Host が閉じるため
- **拒否には理由を添える。** 文面は事実のみの1文で、**行動指示は入れない**。❌ の押下には
  「拒否した」以上の情報が無く、毎回同じ指示を注入するとモデルの判断を奪うため。実機では、
  指示を書かなくてもモデルは再試行せず代替案を出して指示を仰いだ
- **Studio が回答を持たない場合は必ず 204 へ縮退させ、ターミナルに委ねる**
- 診断ログを1行だけ出す（`behavior` / `answered` / `waiting`）。**要求内容・token・識別子は出さない**

実機で確認した経路（ファイルログの実測値）:

```text
07:45:58  承認待ちに入る
07:46:09  claude approval decision dispatched behavior="allow" answered=true waiting=0
07:46:09  作業中に戻る   ← 決定の 0.38 秒後
```

### 9.3 「常に許可」

**2026-09-06、「Claude Code では提供しない」という判断を撤回した。実装済み。**

撤回の理由は、見送りの根拠だった2点が実測で否定されたことにある。当時の根拠は 2026-08-08 の
たった1件の観測にもとづいていた。

| 見送り時の根拠 | 2026-09-06 の実測 |
|---|---|
| `ruleContent` が完全一致の文字列で実効性が乏しい | `//c/temp/**` のような**ワイルドカード**や、フォルダ単位の `addDirectories` が来る |
| `destination: "localSettings"` で恒久権限になる | `destination: "session"`（セッション限定）が来る |

ただし **`localSettings`（恒久）も現役で存在する。** ほぼ同じ「C:\temp を見るだけ」の
コマンドで、一方は `session`、他方は `localSettings` だった。実際に返したところ、
プロジェクトの `.claude/settings.local.json` が作成されルールが書き込まれた。
**ユーザーは要求の見た目から区別できない。**

#### 実装

- hook body の `permission_suggestions` を `PendingApprovalBody` に**不透明値のまま**保持する。
  観測された種類は `addRules` / `setMode` / `addDirectories` の3通りで、件数も宛先も要求ごとに
  変わる。**Codex の `availableDecisions` と同じく、中身を作り変えてはならない**
- 候補が非空のときだけ `available_decisions` を `[allow, allow_with_permissions, deny]` の
  3要素にする。**`allow` は必ず index 0**（既定選択が「常に許可」になってはならない）、
  **`deny` は必ず末尾**（§6.2 の拒否側探索が完全一致 `"deny"` を探すため）
- 選ばれたら `{"behavior":"allow","updatedPermissions":[<候補をそのまま>]}` を返す。
  **キー名 `updatedPermissions` は実測で確定した値**（KO-3 の Q5 は当時 ⏸ のままだった）
- **候補を1件ずつ選ばせない。** ターミナルも複数候補を1つの選択肢としてまとめて適用しており、
  片方だけ適用しても残ったもう一方の条件で次も聞かれる

#### ラベルは必ず適用範囲を出す

**安全上の要件であって親切心ではない。** キー1つで恒久的な権限が付く経路が実在するため。

| 候補の `destination` | HUD のラベル |
|---|---|
| すべて `session` | `allow + always (this session)` |
| `localSettings` を含む | `allow + always (saved to project settings)` |
| 未知の値 | 生の値をそのまま並べる（**言い換えない**） |

`type: "setMode"` を含むときは `mode: acceptEdits` のように付記する。セッションの承認モード
そのものが変わる副作用は、押す前にユーザーへ伝わるべきため。

#### Codex

`proposedExecpolicyAmendment` はプログラム単位（`mkdir`）で実効性があり、提供は検討可。未実装。
Codex の decision は不透明値をそのまま返す契約なので、**理由やフィールドを添える余地は無い**。

### 9.4 二重回答の調停

**ターミナルと HUD の両方が生きているため、先に確定したほう1件だけを採用する排他制御が要る。**

- 要求ごとに状態を持ち、`Pending → Resolving → Resolved` を1回だけ通す
- Codex: HUD/CLIのどちらから回答が来ても、`Pending`を先に`Resolving`へ変えた側だけをApp Serverへ
  転送する。遅着responseは記録したうえで破棄する
- Codex: `serverRequest/resolved`を受信したら、未処理のHUD操作を無効化してHUDを閉じる
- Claude Code: hook の応答を返す直前に、ターミナル側で既に解決していないかを確認する
- Codexは最初からCLIへ転送するため、**30秒後の遅延転送は設けない**

### 9.5 ターミナルが先に答えたことを知る方法（Claude Code）

**2026-09-07 の実機検証で確定。Claude Code は、ターミナルで拒否されても hook を1つも送ってこない。**
拒否したあと 6 分間、`PermissionDenied` も `PostToolUse` も `Stop` も届かなかった。
`PermissionDenied` は plugin に登録済みだが、**一度も観測されていない**。

代わりに使える合図が1つある。**hook 接続が閉じることである。**

| ターミナルでの操作 | hook 接続 | そのあと届く hook |
|---|---|---|
| **拒否** | **即座に閉じる**（要求の 10.7 秒後＝押した瞬間） | **無し** |
| **許可** | 開いたまま | 道具の完了後に `Stop` / `PostToolUse` / `PostToolBatch` |
| **放置** | **開いたまま**（3 分半後も開いている） | `Notification` のみ |

放置した要求の接続が開いたままであることを対照実験で確認しているため、
**接続の切断は「ターミナルで拒否された」合図として使える。**

- 待機中に接続の読み取り側が終端したら、その時点で待機を終える
- **記録・cancel の前に、その待ち口がまだ自分のものかを `try_recv` で確かめる。**
  同じ session の再送要求が同じ token で待ち口を置き換えるため、確かめずに後始末すると
  **新しい要求の待ち口とストアのエントリを消してしまう**
- 許可のときは接続が閉じないので、この経路は通らない。将来閉じるようになっても、
  表示が一時的に待機側へ倒れるだけで、道具の完了 hook が届いた時点で自然に直る

### 9.6 答えられなくなった要求の取り下げ

Studio が回答を届けられなくなる経路は2つある。**どちらも HUD の申し出を取り下げる。**
残しておくと「押しても何も起きない HUD」になり、これは無反応そのものより悪い。

| 理由 | 起きること | セッションの状態 |
|---|---|---|
| `connection_closed` | ターミナルで拒否された（§9.5） | **ターンを終わらせて待機へ。** 拒否後の Claude Code はプロンプトで入力待ちであり、許可を求めていた道具は完了 hook が来ないまま `active_items` に残るため、そのままだと待機中のセッションが「実行中」表示で回り続ける |
| `decision_timeout` | 誰も答えないまま Host の待ちが尽きた | 承認要求だけを落として再計算（＝汎用の作業中）。**結末が分からない**ため、承認待ちを名乗り続けない。代償として「答えてほしい」黄色い合図は戻らない |

**ScreenKey の黄色い点滅は、申し出を取り下げるまでは維持する。** ターミナルでは本当に承認待ちだからである。

## 10. Host 状態機械

`AiDisplaySlots` の隣に、単一インスタンスの「HUD 対象」状態を置く。

| 遷移 | 条件 |
|---|---|
| 対象を設定 | 待機中セッションの ScreenKey 短押し、または待機が1件だけになったとき自動 |
| 対象を解除 | 回答した／外部で解決された／セッション終了／デバイス切断／監視停止 |

- **HUD の表示自体はセッションごとではなく1つ。** 対象を切り替えて中身を差し替える
- 待機中セッションが複数あっても、ScreenKey は全件が自分の状態を表示し続ける
  （HUD だけが1件を指す）
- 解除時は全 slot の `AI_CLIENT_STATE` を full send で再送する
  （既存の selection epoch と同じ手法）

| `AI_CLIENT_STATE` | 8 → **9バイト**（末尾に ScreenKey 表示状態 1バイト）。**実装済み** |
| capability | **bit 14** `AI_CLIENT_SCREENKEY_STATE` を新設。**実装済み** |
| `HOST_ACTION` uplink | 変更なし。既存の `action_id` / `value` を使う |
| `APP_LAYER` | **使わない**（§6.4） |
| 送信方式 | **同報のまま**。unicast はしない（§8） |
| 新規 packet type | **不要** |
| protocol version | **変更なし** |

**文字列を wire へ載せる経路は作らない。**

### uplink の解釈

| 条件 | 動作 |
|---|---|
| 待機中 slot の ScreenKey 短押し | HUD 対象を設定 |
| それ以外の ScreenKey 短押し | `FocusAiTerminal`（現行どおり） |
| ✅ | ハイライト中の選択肢を送信 |
| ❌ | 拒否側へハイライトを移動（送信しない） |
| エンコーダ回転 | ハイライトを移動 |
| いずれも対象が無ければ | 無視してログ（`HudNoop` と理由） |

**Firmware は AI の request ID も選択肢も保持しない。**

### 表示状態の送信タイミング

表示状態は `activity_state` が変わらなくても変化する（HUD 対象の切り替え、保持の期限切れ）。
そのため **表示状態が前回送った値と変わったスロットは、その場で full send する**。
これが無いと、次の定期再送（5 秒）まで届かない。承認待ちが 2 件同時のとき、
ScreenKey を押しても白い L 字が最大 5 秒動かず、§8 の目的をそのまま失う。

さらに、**物理キーの押下に起因する変化は次の周期（最大 500ms）を待たずに即時送信する**。

| 契機 | 送るスロット |
|---|---|
| ✅（`HudConfirm`）が回答を確定した | そのスロット（値 3） |
| ScreenKey 短押しが HUD 対象を切り替えた | **新旧 2 つのスロット** |

対象切替で新しい方だけを送ると、**古い方の白い L 字が次の周期まで消えず、
2 枚が同時に対象に見える**。❌ とエンコーダ回転は対象スロットを変えないため、即時送信しない。

### 実機で使う `action_id`（aipad）

`action_id` の意味は Host の Settings で決まり、**Firmware は番号を送るだけ**である。

| `action_id` | Host 側のアクション | `value` |
|---|---|---|
| 1 | `focus_ai_terminal` | 表示スロット（現在どのキーからも送っていない） |
| 2 | `hud_confirm`（✅） | 0 |
| 3 | `hud_reject`（❌） | 0 |
| 4 | `hud_previous` | 0 |
| 5 | `hud_next` | 0 |
| 6 | `select_hud_target`（ScreenKey ×4） | **表示スロット 0〜3** |

2026-09-06 より、この割当は **Keylink Studio のキーマップ編集から変更できる**
（`host_action` behavior に対応済み）。Firmware の焼き直しは不要。

## 12. 安全性と設定

| 項目 | 方針 |
|---|---|
| 既定 | **無効。** Settings から明示的な警告つき opt-in |
| 権限 | 既存 host action の制約を継承（device 単位の許可リスト、監視中のみ、同一 `seq` は1回） |
| 誤爆防止 | HUD 出現直後 400ms は ✅ を受け付けない（**実装済み・実機確認済み**）。❌ には掛からない（送信しないため） |
| 「常に許可」 | **Claude Code は実装済み**（§9.3）。単押しの3つ目の選択肢として出すが、**適用範囲を必ずラベルに出す**（`this session` / `saved to project settings`）。Codex は未実装 |
| 中断 | **❌ → ✅ の 2 打鍵**（`cancel` を明示的に選んで送る）。長押しは使わない（§6.5） |
| 縮退 | 失敗時は必ずターミナルへ委ねる。**自動許可へ倒さない** |
| 監査ログ | セッション、要求種別、押下、送出可否、失敗理由を記録 |
| 機微情報 | **コマンド文字列や書き込み内容が Studio の UI に表示される**（新規の経路）。ログへ残すか、画面共有時の伏字モードを別途決める |

### 段階2：完了（2026-09-06）

2026-09-05、実Codex CLI（`codex-cli 0.153.2`）＋本番Tauri GUIでBrokerライフサイクルを確認した。
ただしこの検証経路は`respond_to_codex_approval`の直接invokeであり、400 ms guardと物理キーの
経路は通っていなかった。

**2026-09-06、実HID（aipad）で残りを通し、段階2は完了した。** 確認した項目：

- ScreenKey 短押しによる HUD 対象の切り替えと、承認待ちでないときのターミナル前面化
- ✅ 単押しでの承認。`codex activity ... reason=RequestResolved` が**1 回だけ**（二重転送なし）

- **❌ による拒否側へのハイライト移動と、続く ✅ での `cancel` 送信**
- エンコーダ回転によるハイライト移動

段階2 の実装で設計から変わった点は §6.2（❌ の意味）、§6.4（レイヤ切替の取りやめ）、
§6.5（長押しの不使用）、§8（種別アイコンの取りやめ、同報の採用）に反映済み。

### 段階4：一部を前倒しして完了（2026-09-06）

ScreenKey の 9バイト拡張と対象表示・確定演出は、**段階3 より先に着手した**。段階2 で
ScreenKey が「対象を選ぶキーなのにフィードバックを返さない」状態が実機で明らかになったため
（§8）。種別アイコンと `APP_LAYER` 切替は段階4 から取り除いた。

**2026-09-06、Host・Firmware とも実装し、実HID で受け入れた。** 確認した項目：

- 9バイト payload の授受（capability bit 14・13・11 の握手を含む）
- 対象／非対象の読み分け。明るさと白い L 字で**意図どおりの向きに読めること**
- ✅ の確定演出が最後まで描き切れ、二度再生されないこと
- 確定演出中にロゴが消え、完了後に戻ること。図柄が見切れないこと
- ScreenKey 短押しによる対象切替が、押した瞬間に反映されること
- 4 枚の点滅が同位相で、明暗が逆に見える瞬間が無いこと
- 承認待ちでない ScreenKey 短押しでのターミナル前面化（段階2 の回帰）

段階4 の実装で設計から変わった点は §8 に反映済みである。**3 つとも実機でしか分からなかった。**

1. **「静止＝対象」の破棄。** 動いている方が対象だと読まれた（§8「なぜ『静止＝対象』をやめたか」）
2. **Host が値 3 を 1 回でなく 850ms 保持する。** 1 回だと直後の状態変化で演出が消える
3. **確定演出を外周のリングから中央のバッジへ。** 外周はキーキャップの縁で見切れる

### 段階3：完了（2026-09-06）

Claude Code の decision 経路と first-wins 調停を実装し、実HID で受け入れた。あわせて §9.3 の
「常に許可」も実装している（当初は対象外だったが、見送り判断の撤回にともない前倒しした）。

確認した項目：

- HUD に Claude Code の要求が出て、許可／拒否がキーボードから通る（ログの `answered=true` で裏取り）
- **セッション限定と恒久がラベルで区別できる**
- 「常に許可」が実際に効き、同じ操作で二度目は聞かれない
- 恒久を選ぶとプロジェクトに `.claude/settings.local.json` が作られる
- 候補が無い要求では従来どおり2択のまま
- 400 ms guard が効き、ターミナル先着時に二重実行されない
- 拒否理由がモデルへ届き、モデルは再試行せず指示を仰ぐ
- 他の hook の観測（セッション状態表示）が壊れていない

first-wins は、ターミナルが先に答えると `PostToolUse` / `PermissionDenied` が届き、
`ClaudeApprovalBodyConsumer` が待ち口を取り下げる形で成立している。**待ち口が1つしか無いため、
構造上二重に答えられない。**

### 段階4：完了（2026-09-07、実HID受け入れ）

**ScreenKey の Claude Code 対象表示を実装し、段階4 の残りを塞いだ。** 「どのスロットが HUD の
対象か」を答える述語が Codex 専用だったため、HUD 対象が Claude Code のときは全スロットが
「対象でない」表示（値2）のままだった。判定をクライアント非依存の入口 1 本
（`actions::hud_target_for_slot` / `HudTargetSession`）へ寄せ、Codex 側の述語の隣に 2 本目を
作らない形にしてある（§8、2026-09-04 の再発防止）。

表示だけでなく、同じ述語に依存していた 2 つも同時に直った。

- ScreenKey 短押しで Claude Code の HUD 対象を選べる（それまではターミナル前面化に落ちていた）
- ✅ の確定演出（値3）が、答えたスロットで再生される

確認した項目：

- Claude Code の承認待ちで、対象の 1 枚だけが明るい黄枠＋白い L 字になる
- ScreenKey 短押しで対象が切り替わり、古い方の白い L 字が同時に消える
- ✅ / ❌ が Claude Code の要求に効き、確定演出が出る
- 承認待ちでないスロットの短押しは従来どおりターミナル前面化（段階2 の回帰）

### 承認ライフサイクルの3つの不具合（2026-09-07、実機で発見・修正）

段階4 の実機確認で、**表示が事実より長く残る**問題が 3 つ出た。いずれも要求が届いてから
誰かが答えるまでの窓で起きる。

1. **承認待ちが約 120 秒で「作業中」表示に化けた。** `ClaudeSessionReducer::tick` の
   detail-stale 規則が、人間が考えているあいだの無音を「見失った」と取り違えていた。
   未解決の要求を持つセッションは規則の対象外にした（§9.6）
2. **キーボードから答えられるのは 55 秒だけだった。** それを過ぎると Host は 204 へ降りて
   接続を手放しているのに、HUD は要求を出したままで、押しても無反応だった
   （実測 `answered=false waiting=0`）。待ちを約 10 分へ延ばし（根拠は
   `docs/claude-permission-hook-gate-results.md` §Q6）、切れたときは申し出を取り下げる（§9.6）
3. **ターミナルで答えても HUD と黄色い点滅が消えなかった。** Claude Code は
   ターミナル拒否のとき hook を 1 つも送ってこない。代わりに hook 接続を閉じるので、
   それを合図にした（§9.5）

あわせて、**再送要求の待ち口を古い接続の後始末が取り消してしまう**不具合も直した
（再送された要求がキーボードから答えられなくなる。追加したテストで発見）。
